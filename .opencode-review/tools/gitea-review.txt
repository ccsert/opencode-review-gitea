Submit a code review on a Gitea/Forgejo pull request.

First fetch the diff in this run. Submission uses that captured base/head snapshot,
validates line anchors, and refuses a changed PR. Repeated submissions reuse the
confirmed review. PR_CHANGED requires a new run. SUBMISSION_UNKNOWN must never be
worked around with another write tool: publication may already have succeeded.
Success means the review and its line comments have been read back from Gitea.

Runtime REVIEW_MODE controls delivery. In draft mode this tool saves a PENDING
review and exports a local Markdown summary. It never approves or publishes.
The reviewer must use the same account, copy the exported summary into the native
review form, edit the pending comments and manually submit. Stop after a verified
draft result, including a reused or already manually submitted draft. Conflicts
and manual edits must be resolved by the human; never try another write path.

In the default submit mode this tool submits a review with:
1. A summary/report (AI-generated, displayed as the main review body)
2. Line-level comments attached to specific code lines
3. An approval decision (approve/comment/request_changes)

**IMPORTANT**: The `summary` parameter should contain a complete, well-formatted review report. 
The tool does NOT auto-generate content - you control the entire output.

## Summary Format

Write the summary in the format defined by the Review Template section at the start
of the diff output, and decide `approval` by that template's decision rules. Omit
sections without content and use real line breaks. Every diff page must have been
read in this run (REVIEW_INCOMPLETE otherwise).

Comment bodies and suggestions are published exactly as given: write code such as
`printf("a\n")` as it should appear, without extra escaping.

## Line Comments

Use structured tags for categorization:
- `**[BUG:HIGH]**` - Bug with severity
- `**[SECURITY:CRITICAL]**` - Security issue
- `**[PERFORMANCE:MEDIUM]**` - Performance concern
- `**[STYLE:LOW]**` - Style suggestion

Categories: BUG, SECURITY, PERFORMANCE, STYLE, DOCS, TEST
Severities: CRITICAL, HIGH, MEDIUM, LOW

## Example Usage

\`\`\`json
{
  "owner": "org",
  "repo": "project", 
  "pull_number": 42,
  "summary": "## Code Review Report\n\n### 📋 Overview\nThis PR adds user authentication. Overall implementation is clean, but has 1 critical security issue and 1 medium performance issue.\n\n### 🔴 Critical Issues (CRITICAL)\n> Must fix before merge\n\n| Issue | File | Description |\n|:------|:-----|:------------|\n| Plaintext password storage | `src/auth.ts:25` | Password stored without hashing, severe security risk |\n\n### 🟡 Medium Priority (MEDIUM)\n> Recommended to fix\n\n| Issue | File | Description |\n|:------|:-----|:------------|\n| Database connection leak | `src/db.ts:58` | Connection not closed, may exhaust connection pool |\n\n### 💡 Suggestions\nFix all security issues before merge, especially password storage.",
  "comments": [
    {
      "path": "src/auth.ts",
      "line": 25,
      "body": "**[SECURITY:CRITICAL]** Password should be hashed using bcrypt.",
      "suggestion": "const hash = await bcrypt.hash(password, 10);"
    }
  ],
  "approval": "request_changes"
}
\`\`\`

## Parameters

- owner: Repository owner (required)
- repo: Repository name (required)
- pull_number: PR number (required)
- summary: Complete review report content (required) - AI generates this
- comments: Array of line-level comments (optional)
- approval: "comment" (default), "approve", or "request_changes"
